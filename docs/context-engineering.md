# 上下文工程设计思路

> **文档目的**: 记录上下文工程的设计理念、架构思路和演进方向
> **创建时间**: 2025-02-09
> **状态**: 活跃开发中，部分功能已实现
> **最后更新**: 2026-03-02

---

## 核心理念

**上下文工程 = 在合适的时间、从合适的地方、获取合适数量的相关信息**

这不是简单的"存储和检索"，而是**智能的信息组装系统**。

---

## 一、数据分类的四象限

按**访问频率**和**数据类型**把上下文数据分成四类：

```
┌─────────────────────────────────────────────────────────┐
│                    高频访问                              │
├───────────────────────┬─────────────────────────────────┤
│                       │                                 │
│   🔥 热数据            │   💡 索引数据                   │
│                       │                                 │
│   • 当前会话状态       │   • 任务索引                    │
│   • Agent运行时变量    │   • 文件索引                    │
│   • 最近几条消息       │   • Artifact索引               │
│                       │   • 向量索引                    │
│   【内存】             │   【内存 + 缓存】               │
│                       │                                 │
├───────────────────────┼─────────────────────────────────┤
│                       │                                 │
│   📦 历史数据          │   🎯 语义数据                   │
│                       │                                 │
│   • 完整对话历史       │   • 文档向量                    │
│   • 任务执行记录       │   • 代码片段向量                │
│   • 历史配置           │   • 对话摘要向量                │
│                       │   • 多模态向量                  │
│   【数据库】           │   【向量数据库】                │
│                       │                                 │
└───────────────────────┴─────────────────────────────────┘
        低频访问                    非结构化/语义化
```

### 维度1：按数据结构分类

1. **结构化数据** (Structured Data)
   - 任务配置、参数、状态
   - 用户设置、偏好
   - 系统配置、元数据

2. **半结构化数据** (Semi-structured Data)
   - 对话历史（消息列表）
   - 执行日志（步骤记录）
   - Artifact索引（文件/函数调用）

3. **非结构化数据** (Unstructured Data)
   - 代码文件内容
   - 文档内容
   - 多模态数据（图片、音频、视频）

4. **语义向量数据** (Vector Embeddings)
   - 文档embedding
   - 代码片段embedding
   - 对话摘要embedding

### 维度2：按时效性分类

| 数据类型 | 时效性 | 示例 |
|---------|-------|------|
| **实时数据** | 毫秒级 | Agent运行状态、变量值 |
| **会话数据** | 分钟级 | 当前会话对话、未完成任务 |
| **持久数据** | 永久 | 用户配置、历史记录 |

## 二、存储介质的选择逻辑

### 选择原则：**访问速度 vs 存储成本 vs 查询能力**

| 存储介质 | 擅长 | 不擅长 | 典型场景 |
|---------|------|--------|----------|
| **内存** | 极快访问 | 容量小、断电丢失 | 当前会话、热数据缓存 |
| **Redis** | 快速、分布式 | 复杂查询弱 | 会话状态、分布式锁 |
| **关系数据库** | 结构化查询、事务 | 语义搜索弱 | 任务配置、消息记录 |
| **向量数据库** | 语义相似度搜索 | 精确匹配弱 | 找相似文档、相关历史 |
| **文件系统** | 大文件存储 | 实时查询差 | 原始文件、导出数据 |

### 一句话总结：
- **要快 → 内存**
- **要稳 → 数据库**
- **要智能 → 向量DB**
- **要大 → 文件**

## 三、上下文工程的三层架构

```
┌─────────────────────────────────────────────────────────┐
│                                                      │
│              应用层：Agent、Task、Skill                  │
│              （按需请求上下文）                           │
│                      ↑                                  │
└──────────────────────┼──────────────────────────────────┘
                       │
                       │ "我需要关于XXX的信息"
                       │
┌──────────────────────▼──────────────────────────────────┐
│                 编排层                              │
│                                                           │
│   智能决策：从哪里获取？获取多少？如何组合？              │

│   │ 元数据检索    │  │ 语义检索      │  │ 混合编排     │ │
```

### 编排层的核心职责

1. **理解需求**：Agent要做什么？需要什么信息？
2. **多路检索**：同时从多个存储获取数据
3. **智能融合**：合并、去重、排序、裁剪
4. **动态调整**：根据场景改变策略

## 四、上下文获取的四种策略

### 策略1：**时序检索**（最常用）

"给我这个任务最近10条消息"

- 按时间顺序获取最近N条记录
- 存储：关系数据库
- 适用场景：简单对话延续

### 策略2：**关键词检索**

"给我所有提到'文件上传'的消息"

- 全文搜索特定关键词
- 存储：关系数据库 + 全文索引
- 适用场景：查找特定主题的讨论

### 策略3：**语义检索**

"给我跟'如何优化数据库'相关的历史讨论"

- 向量相似度搜索，找到语义相关的内容
- 存储：向量数据库
- 适用场景：跨领域的问题求解

### 策略4：**混合检索**（最强大）

"给我相关的历史记录，优先最近的，但要跟主题相关"

- 结合时序、关键词、语义三种方式
- 智能加权排序
- 存储：多种存储联合使用
- 适用场景：复杂任务、跨任务延续

## 五、一个完整的上下文请求流程

假设Agent说："帮我修复一个bug，需要知道之前做了什么"

```
【第1步】理解需求
├─ 任务类型：bug修复
├─ 需要的信息：
│  • 最近的对话历史（时序）
│  • 相关的代码修改（语义）
│  • 文件操作记录（元数据）
│  • 之前的错误和解决方案（语义）

【第2步】并行获取
├─ 从内存获取：当前会话状态
├─ 从数据库获取：最近20条消息
├─ 从向量DB获取：与"bug"相关的历史
└─ 从数据库获取：文件修改记录

【第3步】智能融合
├─ 去重：同一条消息只保留一份
├─ 加权排序：
│  • 最近的消息权重高
│  • 语义相关性高的权重高
│  • 包含错误消息的权重高
└─ 裁剪：控制总长度不超过预算

【第4步】返回上下文
└─ 打包成结构化数据返回给Agent
```

## 六、上下文的动态优化

### 问题：上下文不是静态的，需要动态调整

### 解决方案：三级优化

**Level 1: 缓存优化**
- 刚用过的数据，存起来下次直接用
- 减少70%的重复查询

**Level 2: 压缩优化**
- 对话太长时，自动压缩成摘要
- 保留关键信息，丢弃冗余细节

**Level 3: 智能筛选**
- 不是所有历史都重要
- 根据当前任务，动态筛选最相关的内容

## 七、不同场景的上下文策略

### 场景1：简单问答

用户："这个函数是做什么的？"

**上下文策略**：
- 只需要最近的几条消息
- 时序检索即可
- 不需要语义搜索

### 场景2：代码重构

用户："帮我重构这个模块"

**上下文策略**：
- 需要完整的模块历史
- 语义检索找相关代码
- 加载之前的讨论和决策

### 场景3：Bug调试

用户："有个bug，帮我找一下"

**上下文策略**：
- 最近的错误消息（高优先级）
- 相关的代码修改历史
- 之前的类似问题和解决方案

### 场景4：跨任务延续

用户："上周我们讨论的那个功能，继续做"

**上下文策略**：
- 跨越时间范围的语义检索
- 会话级别的上下文继承
- 加载相关的历史任务摘要

## 八、技术选型的宏观建议

### 最小可用方案（MVP）

内存 + 关系数据库

- 适合：单用户、简单场景
- 实现：你现在的架构基本够用
- 优化：添加缓存层即可

### 进阶方案

内存 + 关系数据库 + 向量数据库

- 适合：多用户、复杂任务
- 新增：语义检索能力
- 收益：智能化程度大幅提升

### 企业级方案

完整的多层架构 + 缓存 + 消息队列 + 分布式存储

- 适合：高并发、大规模
- 复杂度：需要专业团队维护

## 九、上下文工程的核心挑战

### 挑战1：**相关性 vs 覆盖面**

既要覆盖全面，又要高度相关

**解决**：智能排序和动态裁剪

### 挑战2：**新鲜度 vs 压缩**

既要保持最新状态，又要控制长度

**解决**：分层压缩（热数据全量，温数据摘要）

### 挑战3：**性能 vs 准确性**

既要快速响应，又要检索准确

**解决**：缓存 + 异步预处理

### 挑战4：**成本 vs 质量**

既要控制成本（API调用、存储），又要保证质量

**解决**：混合策略（规则 + AI）

## 十、当前项目的实现现状

### 已完成功能 (2026-03-02)

#### 1. 用户画像系统 ✅

**实现文件**: `src/core/task/hooks/user-profile-accumulator.ts`

**功能特性**:
- `UserProfileAccumulatorHook`: 通用用户画像累积 Hook
  - `preExec`: 从 users 表加载 userId 的 userProfile，注入到 workingMemory
  - `postExec`: 提取本次会话特征，累积通用字段到用户画像
- 支持的画像字段:
  - `preferences`: 用户偏好 (简洁回复/详细回复)
  - `habits`: 用户习惯 (夜间活跃/日间活跃/长时间会话)
  - `tags`: 用户标签 (新用户/活跃用户/高活跃)
  - `data.behavior`: 行为统计 (总会话数，向后兼容)

**数据库支持**:
- `users` 表存储用户基本信息
- `user_profiles` 表存储用户画像数据

#### 2. Context API ✅

**实现文件**: `steps/api/context-api.step.ts` 等

**API 端点**:
- `GET /api/contexts/:taskId` - 获取任务上下文
- `GET /api/sessions/:sessionId` - 获取会话上下文
- `GET /api/users/:userId` - 获取用户画像
- `POST /api/contexts/:taskId/compress` - 手动触发上下文压缩
- `GET /api/contexts/:sessionId/messages` - 获取会话消息历史
- `GET /api/contexts/:sessionId/outputs` - 获取会话产物
- `GET /api/contexts/:sessionId/artifacts` - 获取会话 Artifact

#### 3. 前端上下文视图 ✅

**实现文件**: `motia-frontend/src/components/ContextTab.jsx`

**功能特性**:
- 三个子 Tab: Task Context / Session Context / User Context
- Task Context: 显示任务上下文、消息历史、压缩摘要
- Session Context: 显示会话信息、执行历史
- User Context: 显示用户画像、偏好、习惯、标签
- 自动加载: 从 taskContext 获取 sessionId，再加载 session 和 user 数据
- 防止无限加载: 修复了没有 userId 时的无限加载状态

### 现有架构

```
数据库层
  - SQLite/PostgreSQL存储
  - tasks, task_contexts, messages, artifacts表
  - users, user_profiles表 (新增)

业务层
  - ContextManager: 统一管理上下文
  - ContextCompressor: 智能压缩
  - LLMSummarizer: LLM摘要生成
  - ArtifactExtractor: 文件和函数调用索引
  - UserProfileAccumulatorHook: 用户画像累积 (新增)

应用层
  - ContextManagerTaskHook: 任务生命周期钩子
  - UserProfileAccumulatorHook: 用户画像钩子 (新增)
  - Agent: 按需获取和使用上下文

API 层 (新增)
  - Context API: 上下文查询接口
  - 用户画像 API: 用户数据查询接口

前端层 (新增)
  - ContextTab: 上下文视图组件
```

### 数据流

```
用户输入
  → Agent处理
  → ContextManagerTaskHook.preExec (创建上下文)
  → 从数据库继承历史上下文
  → 任务执行...
  → Agent.conversationHistory (内存状态)
  → ContextManagerTaskHook.postExec (同步到数据库)
  → 检查是否需要压缩
  → LLMSummarizer.summarize (调用LLM API)
  → ContextCompressor.compress
  → DataStore.save (持久化)
  → 前端实时更新 (WebSocket)
```

### 优点

- ✅ 智能化：自动压缩、LLM摘要、会话继承
- ✅ 完整性：完整消息历史、Artifact跟踪
- ✅ 实时性：WebSocket实时推送、增量同步
- ✅ 持久化：多数据库支持、事务级别一致性

### 存在的问题

**性能瓶颈**：
- LLM压缩开销大（每次压缩调用API）
- 数据库N+1查询
- 缺少缓存机制
- 深拷贝大对象

**架构耦合**：
- 强依赖全局单例
- 组件间直接实例化
- 职责混合

**并发安全**：
- 全局锁导致串行化
- 没有事务保护
- 简单的消息比较逻辑

**代码质量**：
- any类型滥用
- 重复的ID生成代码
- 测试覆盖不足
